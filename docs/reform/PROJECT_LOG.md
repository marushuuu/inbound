## 1. プロダクト概要(確定)

リフォーム会社の**営業担当**が使う SaaS。スコープは **現場調査(ヒアリング)〜 契約** まで。

- 販売形態: リフォーム会社向けSaaS(自社ツールではない)
- 主要ユーザー: 営業担当(現場はスマホ/タブレット、社内はPC)
- 対象工事: **Fast系(水回り・住設交換)から着手**。リノベ系(間取り変更・3Dスキャン要)は後続フェーズ
- 参考データ: 実際の見積書PDF(浴室・洗面改装工事 ¥1,903,000)、業界KPI・業務フロー資料、ANDPAD技術ブログ

### 1-1. Fast系の業務フロー(確定・実装済み)

```
ヒアリング → (簡易現調) → 見積作成(松竹梅) → 施工日時の調整 → 契約締結
```

※当初「見積 → 契約」だった導線に、**「施工日時」ステップを追加**(契約前に担当者の空き状況を見ながら施工日を確定させたいという要望による)。現在のステップ順は **ヒアリング → 見積 → 施工日時 → 契約**。

### 1-2. リノベ系(後続フェーズ・未着手)

```
ヒアリング → 3Dスキャン → (イメージ作成 → 図面起こし → 積算) → 見積(スコープ型松竹梅) → 契約
```

Fast系と基盤(見積・契約・検索)を共有し、3Dスキャン〜積算工程のみ追加する設計。

## 3. データモデル(確定・実装済み)

サンプル見積書の構造(表紙 → 内訳 → 工事種別ごとの大項目 → 明細行)を反映。

- **Project(案件)**: 顧客名、工事タイトル、物件情報(築年数・構造)、ステータス、ヒアリング、選択中の見積パターン、設備グレードの差し替え、実施工事項目(taskIds)、施工日時(schedule)、契約情報
- **Hearing(ヒアリング)**: きっかけ・悩み(複数選択)、予算帯、予算上限、希望時期、過去のリフォーム履歴、キーマン同席、変動リスクメモ ※**このうち複数項目に変更要望あり(§7参照、未実装)**
- **Product(商品マスタ)**: カテゴリ、メーカー、商品名、型番、価格、グレード順位・ラベル、特徴。カテゴリ内でグレード系列(松竹梅の元)を構成
- **WorkLine(見積明細行)**: 工事種別の大項目 × 名称・仕様・金額(サンプル見積書の実データを移植)
- **WorkItem(工事マスタ)**: 工事項目ごとの**所要時間(分単位)**、工事種別、職種(担当者マッピング用)。施工日時の自動割付の元データ
- **Worker(担当者)**: 氏名、職種、自社/協力業者の別
- **ScheduleState(施工日時)**: 日付、開始/終了(分)、担当者ごとの割付タスク、Googleカレンダーの仮予定イベントID
- **ContractState(契約)**: 説明確認チェック3項目、署名(Canvas手書き)、締結日時
- **PastEstimate(過去見積)**: 検索・類似度スコアリングの対象データ

## 4. 技術方針(確定)

- **ANDPAD連携は言語非依存**: ANDPADのREST API経由になるため、こちらの実装言語は連携可否に影響しない。連携しやすさは「API層を疎結合に切り出すこと」「ANDPAD側のデータモデルに写像しやすいスキーマにすること」で決まる
- **採用スタック**: Next.js (App Router) + TypeScript + Tailwind CSS v4(本リポジトリの既存プロダクトと統一)。ANDPAD自身もTypeScriptを採用しており親和性が高い
- **DB**: 現状は localStorage のみの**フロントエンドMVP**(認証・DBは未導入)。将来的に PostgreSQL(+ pgvector で類似検索)を導入予定
- **連携・非同期処理層**: 将来 Go でマイクロサービスとして切り出す構想(ANDPADの技術方針に合わせる)。現時点ではNext.jsのAPI Routesで実装(Googleカレンダー連携など)
- **署名**: Canvas手書きサイン(MVP実装済み)。電子契約サービス(クラウドサイン等)への連携は将来検討

## 6. 実装済み機能(`reform-app/`)

Fast系フローが**実際に動くWebアプリ**として動作(スマホ/デスクトップ両対応)。

### 6-1. 画面構成

| Path | 内容 |
| --- | --- |
| `/` | 案件一覧(ステータス絞り込み・案件作成) |
| `/projects/[id]/hearing` | ヒアリングシート(予算・希望時期・履歴を含む。§7で刷新済み) |
| `/projects/[id]/estimate` | 見積作成(松竹梅・設備グレード差し替え・内訳自動計算) |
| `/projects/[id]/schedule` | 施工日時の調整(タイムグリッド・自由入力の日付/時刻・仮押さえ) |
| `/projects/[id]/contract` | 契約(施工日時入り・説明チェック・甲乙両方の手書きサイン・締結) |
| `/projects/[id]/estimate/print` | 見積書帳票(ブラウザ印刷でPDF保存) |
| `/projects/[id]/contract/print` | 工事請負契約書帳票 |
| `/search` | 過去見積の検索(類似度スコア順) |
| `/catalog` | 商品マスタ(グレード系列) |
| `/works` | 工事マスタ(所要時間を分単位で設定) |

### 6-2. 見積 → PDF出力

- 松竹梅3パターンをタップ切替、設備グレードを比較モーダルで差し替えると内訳・合計を自動再計算
- 見積書・契約書とも「PDFとして保存 / 印刷」ボタンからブラウザ印刷機能でPDF化(見積書はサンプルPDFと同じ構成: 表紙・内訳・工事種別ごとの明細・注意事項)

### 6-3. 過去見積の類似度検索

ルールベースの類似度スコア(8点満点): 工事種別一致+3、築年数帯一致+2、予算帯一致+2、構造一致+1。案件のヒアリング内容から自動採点し、スコア降順で表示。将来はベクトル類似検索(pgvector)に置き換える設計。

### 6-4. 施工日時調整 + Googleカレンダー連携(実装済み・②方式)

- 担当者×時間のタイムグリッド(24時間表示、**スマホ30分単位/タブレット・PC15分単位**に自動切替)
- 施工日はカレンダー入力(`<input type="date">`)、開始時刻は時刻入力(15分刻み)で**営業担当が自由に指定**。工事マスタの所要時間(分)からその時刻を起点に工程順で自動割付。自動提案(候補一覧)は削除済み(§7)
- **Googleカレンダー連携(OAuth・自動登録方式)を実装済み**:
  - 担当者ごとにOAuth同意 → その担当者の空き(FreeBusy API)を実データで取得
  - 仮押さえで各担当者のカレンダーに **【仮】** 予定を自動登録
  - 契約締結で **【確定】** にタイトル更新
  - `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` が未設定の間はデモの空きデータで動作(段階的に有効化できる設計)
  - 実装ファイル: `lib/server/google.ts`(OAuth・FreeBusy・イベント登録)、`app/api/google/*`、`app/api/calendar/*`
  - 連携トークンは暫定でファイル保存(`.data/google-tokens.json`)。DB導入時に置き換え予定

### 6-5. 工事マスタ

工事項目ごとの標準所要時間を**分単位**で編集可能(即保存)。Fast系標準セット(撤去・養生60分→洗面台取付120分→クロス補修60分=計240分/4時間)にはバッジ表示。変更は施工日時の自動割付に即反映。

### 6-6. データ永続化

現状は localStorage(ブラウザ内保存)のみ。「デモデータに戻す」ボタンでリセット可能。DB・認証は未実装。

## 7. 直近の変更要望(実装済み)

以下は2026年最新のフィードバックで、**すべて実装済み**(lint・build・E2E動作確認済み)。

### 7-1. ヒアリングシート ✅

1. **予算入力の金額表記化** ✅: 数値入力欄が入力に応じて自動でカンマ区切り金額表記(例: `¥1,234,567`)になるよう実装。内部値は円単位の数値(`Hearing.budget: number | null`)で保持し、表示側で `toLocaleString("ja-JP")` を都度適用
2. **「ご予算の目安」の選択肢チップを削除** ✅: クイック選択チップを廃止し、自由入力の金額欄のみに一本化
3. **希望時期を日付レンジのカレンダー入力に変更** ✅: `<input type="date">` を2つ(開始日・終了日)並べ、ブラウザ標準のカレンダーUIで選択。下に「YYYY年M月D日 〜 YYYY年M月D日」の確認表示も追加(`Hearing.timingFrom` / `timingTo`、`lib/schedule.ts` の `formatFullDateJa`)
4. **過去のリフォーム履歴を年月リスト選択+手入力+複数レコード化** ✅:
   - 年・月をそれぞれ `<select>` で選択、内容は自由入力のテキスト欄
   - 「履歴を追加」ボタンで複数レコードを追加・個別削除可能(`Hearing.history: HistoryRecord[]`)
   - **ANDPAD連携を見据えた設計**: `HistoryRecord.source` を `"manual" | "andpad"` で持たせ、`source: "andpad"` のレコードは入力欄をdisabledにして編集不可(参照のみ)、`"manual"` は通常どおり編集可能。現状は「ANDPADから取得」ボタンでサンプルレコードを1件追加するプレースホルダー実装(実際のANDPAD API連携は未接続。§9の未確定事項に接続ルートの検討を記載)
5. **「キーマン同席」の項目を削除** ✅: `Hearing.keymanTogether` フィールドごと削除

### 7-2. 施工日時調整画面 ✅

6. **カレンダーの自由入力** ✅: 施工日を `<input type="date">`、開始時刻を `<input type="time" step={900}>`(15分刻み)で営業担当が直接指定できるように変更。指定した日時を起点に、工事マスタの所要時間から工程順で自動割付してタイムグリッドに表示(`lib/schedule.ts` の `allocateDay` が `startMin` 引数を受け取るよう変更)
7. **「組める日程の候補」機能を削除** ✅: 自動提案(`findCandidates`)のロジック・UIを削除し、6の自由入力に一本化

### 7-3. 契約画面(請負者側の署名) ✅

8. **請負者(自社)側の署名に対応** ✅: 「都度サイン」「登録済み署名の自動表示」の**両方**を実装。
   - 会社の署名は `useStore().companySignature` としてlocalStorageに永続化(`reform-app.companySignature.v1`、案件をまたいで共有)
   - 未登録の場合は契約画面に手書きサイン欄が表示され、「この署名を登録する」で保存すると以降の**すべての契約で自動的に表示**される(お客様側の署名だけ都度描けば締結できる)
   - 「署名を登録し直す」でいつでも会社署名を更新可能
   - 締結時、その時点の会社署名のコピーを `ContractState.contractorSignature` として案件に保存(後で会社署名を変更しても過去の契約書には影響しない)
   - 契約書PDF帳票(`/projects/[id]/contract/print`)にも甲(発注者)・乙(請負者)双方の署名画像を表示するよう更新
   - 手書きサインの共通ロジックは `components/SignaturePad.tsx` に切り出し、発注者用・請負者用の両方で再利用

> **請負者側サインの法的な考え方(参考・再掲)**: 日本の民法上、契約は当事者双方の意思表示の合致で成立し、書面や署名捺印は契約の成立要件ではないのが原則です。ただし建設工事の請負契約は実務上・信頼性確保の観点から**双方の記名押印(または署名)を交わすのが一般的な慣行**であり、クーリングオフ書面など特定商取引法が絡む場合は交付書面の記載事項が法定されています(押印必須とまでは明記されていません)。したがって「法的に必須」というよりは「実務上・証拠力確保のために双方の署名を残すべき」という位置づけです。この点は最終的に顧問弁護士等へのリーガルチェックを推奨します(`PLANNING.md` §7 の未確定事項にも記載済み)。

## 8. 商品マスタの自動登録(カタログ取込)の検証結果

営業が使うメーカーカタログ(デジタルカタログのキャプチャ画像)から、商品マスタ(シリーズ・品番・定価・寸法・画像)を半自動で登録する仕組みの実現可能性を検証した。

### 検証結果(TOTO・タカラスタンダードの実キャプチャで実施)

- **テキスト項目(シリーズ・品番・定価・寸法)の抽出**: 実用レベル。**メーカーごとにカタログのレイアウトが違っても問題なし**(LLMビジョンに「このスキーマで抜いて」と渡す方式のため、座標依存のテンプレート方式と異なりレイアウト自由)
- **商品画像の切り出し**: 最大の難所。LLMは画像領域の座標指定が不安定なため自動切り抜きは非推奨。現実解は下記のいずれか:
  1. 登録画面で人がキャプチャ上をドラッグして矩形を手動切り抜き(半自動・1商品数秒)
  2. メーカー公式サイトから品番で画像を別途取得
  3. まず画像なしで運用開始
- **条件付き価格・注記**(「※特定品番の場合」等)は抽出できるが、**誤登録防止のため人によるレビュー必須**

### マスタ設計上の論点(タカラのレンジフードカタログから判明)

1. **カラー展開品番**(例: `VUA-601AD(▲)` の▲にカラー記号が入る): 商品マスタは「**親商品 + バリエーション(間口×カラー)**」の2階層で持つのがよい
2. **本体と関連部材の関係**: 「本体+必須別売品(排気金具)+加算オプション(電動シャッター等)+サイズ別部材(前面パネル)」が1カタログに同居する。将来的にマスタを「商品(親) ─ バリエーション ─ 関連部材(必須/任意、加算価格)」へ拡張すれば、見積作成時に「本体を選ぶと必須部材が自動で明細に入る」という実務的な動きが可能になる

### 現時点の合意

**まずは現行の商品マスタ仕様(グレード系列のみ)のまま進めてよい**(ユーザー確認済み)。関連部材・バリエーション対応の拡張は、他メーカーの部材データも登録する段階で改めて設計する。

### 想定する実装フロー(未着手)

「キャプチャをアップロード → Claude APIがスキーマ付きJSONで候補を返す → レビュー画面で人がセル単位に確認・修正(自信が低い項目はハイライト) → 承認で商品マスタに登録」。全自動登録にはせず必ず人のレビューを挟む設計。
