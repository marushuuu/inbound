# リフォーム営業SaaS 企画・要件定義ドキュメント

> **このドキュメントは初期の企画・要件定義(2026-08-30時点)です。**
> それ以降の意思決定・実装状況・未対応の変更要望は [`PROJECT_LOG.md`](./PROJECT_LOG.md) に集約しています。次にこのプロジェクトへ着手する際はまず `PROJECT_LOG.md` を参照してください。

対象スコープ: **現場調査(ヒアリング)〜 契約** までをプロダクト化するリフォーム会社向けSaaS。
主要ユーザーは**リフォーム会社の営業担当**。現場ではスマホ / タブレットで利用する。

入力情報:
- ヒアリング(2026-08-30): SaaS前提、営業が利用、水回り(Fast系)から着手しリノベ系は別フェーズ
- 見積書サンプルPDF(浴室・洗面改装工事 / 約190万円)
- リフォーム業務フロー&業界ナレッジ資料(`reformworkflowtrainingdata.md`)

## 1. プロダクトの2トラック構成(確定方針)

### 1-1. Fast系(水回り・住設交換中心)— 先行開発

3Dスキャン不要。型番・写真ベースで見積もる。

```
施主要望ヒアリング(構造化ヒアリングシート)
  → 簡易現調(写真撮影・既存設備の型番確認・採寸最小限)
  → カタログ連携 or 類似過去見積の検索・一覧化
  → 見積作成(松・竹・梅の複数パターン ※グレード違い)
  → 提示 → その場で電子契約 / サイン取得
  → (オプション)協力業者スケジュールを見ながら工事日を仮決め
```

- 松竹梅は**設備グレードの差し替え**が軸(例: ユニットバス スタンダード/ミドル/ハイグレード)。
  上位グレードの商品画像・仕様をその場で見せられることが重要(アップセルと契約率の両立)。
- 業務フロー資料のベストプラクティスをプロダクトで支援する:
  - 現調は15〜30分で終え、着座打合せに60分使う → **入力が速いUIが必須**
  - 見積は現調から3〜5日以内、少額はその場概算 → **その場で松竹梅概算が出せる**ことが差別化
  - 解体後リスク(追加費用の上限)の事前説明 → 見積に「変動リスク項目」を明示する欄を設ける

### 1-2. リノベ系(間取り変更・空間リフォーム)— 後続フェーズ

要3Dスキャン。

```
施主要望ヒアリング → 3Dスキャン
  → (イメージ作成 → 図面起こし → 積算)
  → カタログ連携 or 類似過去見積検索
  → 見積作成(松竹梅 ※グレードではなく「どこまでやるか」= スコープ違い。キッチンのみ/水回り全部/全面 等)
  → 契約
```

- Fast系と見積・契約・検索の基盤を共有し、3Dスキャン〜積算の工程だけが追加される設計にする。
- 3Dスキャンは自前開発せず、まずは既存ツール(スマホLiDAR系アプリ等)の出力(図面・採寸値)の取り込みから始める。

### 1-3. 認識の確認ポイント

いただいたイメージと基本的に一致。1点だけ補足提案:
Fast系でも「写真撮影+型番記録」という**最低限の現調記録**は残す設計にしたい
(職人への発注時の手戻り防止・追加工事クレーム防止に効くため。業務フロー資料 3-2 の「徹底的な撮影」に対応)。

## 2. 解決する課題(優先順)

| # | 課題 | プロダクトでの解決 |
| --- | --- | --- |
| 1 | 見積作成に2〜8時間かかる | 過去見積DB検索・テンプレート・カタログ連携で「数クリック概算」。目標: 水回り単体はその場、複合でも当日〜翌日 |
| 2 | 上位グレード商品・画像をその場で出せない | 商品マスタに画像・仕様・上位/下位グレードのマッピングを持ち、松竹梅を自動生成 |
| 3 | 契約までのリードタイム | その場で契約書生成 → タブレット手書きサイン or 電子契約で即締結 |
| 4 | 過去見積が資産化されていない | 見積は全て構造化して蓄積。条件(工事種別・築年数・金額帯)+類似検索でレコメンド |
| 5 | 工事日がその場で示せない | 協力業者(差配先)の空き状況カレンダーを見ながら工事日候補を提示(フェーズ後半) |

## 3. データモデル(見積書PDFの構造を反映)

サンプル見積書から抽出した構造: 表紙(見積金額・有効期限・支払条件・注意事項) → 内訳(工事費計・諸経費・値引き・消費税) → 工事種別ごとの大項目(共通/解体・撤去/基礎/大工/内装/電気/水道/住宅設備/諸経費) → 明細行(名称・仕様・数量・単位・単価・金額)。住宅設備はメーカー名・商品名・型番(例: オフローラ 1616 / FANCIO M-753NFNE…)を持つ。

- **Customer(顧客)**: 氏名、連絡先、住所、流入経路、OB顧客フラグ(部位別ライフサイクル提案用)
- **Project(案件)**: 顧客、物件(築年数・構造・ハウスメーカー)、トラック(Fast/リノベ)、ステータス(問い合わせ/ヒアリング済/見積提示/契約/失注)、次アポ日時
- **Hearing(ヒアリング)**: 構造化ヒアリングシート(きっかけ・悩み、過去リフォーム履歴、予算幅、希望時期、キーマン同席有無)※業務フロー資料 3-1 の項目を標準搭載
- **Survey(簡易現調)**: 写真(部位タグ付き)、既存設備の型番、採寸値、変動リスクメモ(解体後に金額が変わりうる箇所)
- **Estimate(見積)**: 案件に紐づく。**パターン(松/竹/梅)× 版番号**で管理。表紙情報(有効期限・支払条件・注意事項)、値引き、諸経費率、消費税
  - **EstimateSection(大項目)**: 工事種別(共通・解体・基礎・大工・内装・電気・水道・住宅設備・諸経費)
  - **EstimateLine(明細行)**: 名称、仕様、数量、単位、単価、金額、商品マスタ参照(任意)
- **ProductMaster(商品マスタ/カタログ)**: メーカー、商品名、型番、定価、仕入価格、画像、カテゴリ、**グレード系列**(同一カテゴリ内の松竹梅候補)
- **PriceMaster(工事単価マスタ)**: 工事項目・標準単価・歩掛かり(パック商品=空間単位の平準化価格も表現)
- **Contract(契約)**: 確定見積参照、契約書PDF、署名データ(手書きサイン画像 or 電子契約ID)、締結日時
- **Partner(協力業者/差配先)** + **ScheduleSlot**: 業種、対応エリア、空き枠
- **Tenant(テナント=リフォーム会社)** / **User(営業担当)**: SaaSなのでマルチテナント前提。等級(業務フロー資料 2-1)を持たせれば承認フロー・ダッシュボードに使える

### 過去見積の検索・レコメンド

- 構造化検索: 工事種別 × 金額帯 × 築年数 × 設備型番 などでの絞り込み(まずはこれで十分効く)
- 類似検索: 見積・ヒアリング内容の埋め込みベクトル化(PostgreSQL + pgvector)で「この要望に近い過去見積」を提示
- 蓄積の立ち上げ: 既存の過去見積(PDF/Excel)のインポーター(構造抽出)を用意し、導入時にデータ資産を持ち込めるようにする ※SaaSのオンボーディングで最重要(業務フロー資料 5 章の移行リスク対策)

## 4. 技術方針(ANDPAD連携を見据えて)

### 4-1. ANDPADの技術スタック(tech.andpad.co.jp 等より)

- バックエンド: **Ruby on Rails のモノリスが中核、新規サービスは Go でマイクロサービス化**を推進
- フロントエンド: **TypeScript**(Vue/Nuxt、React/Next.js)
- モバイル: Swift / Kotlin / Flutter、インフラ: AWS・Kubernetes 等

### 4-2. 重要な前提: 連携は「言語」ではなく「API」で決まる

ANDPADとのデータ連携は ANDPAD が公開する **REST API(ANDPAD API / パートナー連携)経由**になるため、こちらの実装言語が何であっても連携可能性は変わりません。「連携の取りやすさ」で効くのは、(a) API連携層を疎結合に切り出しておくこと、(b) ANDPAD側のデータモデル(案件・見積・受発注)に写像しやすいスキーマにしておくこと、の2点です。

### 4-3. 採用スタック(提案)

| レイヤ | 採用 | 理由 |
| --- | --- | --- |
| アプリ本体 | **Next.js (App Router) + TypeScript** | ANDPADも採用するTS。スマホ/タブレット前提のモバイルファーストWeb(PWA)を最速で出せる。本リポジトリの既存資産とも一致 |
| DB | **PostgreSQL(+ pgvector)** | マルチテナント・見積の階層構造・類似検索まで1つで賄える |
| 連携・非同期処理層 | 将来 **Go** のサービスとして切り出し | ANDPAD連携アダプタ、PDF一括処理、レコメンド計算など。ANDPADのマイクロサービス方針と同じ言語で、採用・知見面でも揃えやすい |
| 帳票 | サーバーサイドPDF生成(見積書・契約書) | サンプル見積書のフォーマットを再現 |
| 署名 | Canvas手書きサイン(MVP) → クラウドサイン/GMOサイン等のAPI連携 | 「その場で締結」を最短で実現し、法的要件が上がる案件は電子契約サービスへ |

方針: **MVPはNext.jsフルスタック(TypeScript)一本で作り切り、ANDPAD連携を本格化するタイミングでGoの連携サービスを切り出す。**

## 5. フェーズ計画

| フェーズ | 内容 | 主要機能 |
| --- | --- | --- |
| Phase 1 | **Fast系MVP** | 案件管理、ヒアリングシート、簡易現調(写真・型番)、見積作成(大項目/明細・松竹梅パターン・版管理)、見積書PDF、過去見積の構造化蓄積+条件検索 |
| Phase 2 | **契約とカタログ** | 契約書PDF生成+その場サイン(電子契約連携)、商品マスタ/グレード系列(上位グレード画像提示)、過去見積レコメンド(類似検索)、過去見積インポーター |
| Phase 3 | **差配とANDPAD連携** | 協力業者スケジュール・工事日候補提示、ダッシュボード(契約率・リードタイム・粗利率 ※業界KPIベンチマーク付き)、ANDPAD API連携(案件・見積データ送出) |
| Phase 4 | **リノベ系** | 3Dスキャン取込→図面・積算補助、スコープ型松竹梅(どこまでやるか)、イメージ提案 |

各フェーズごとに営業担当者に現場で使ってもらいフィードバックを反映する。

## 6. UI/UXの決め方

Claude Design(デザインキャンバス)で主要画面のモックを作成し、見た目を直接確認・微調整しながら固めていく進め方を採用する。

1. 業務フロー・見積構造からClaudeが主要画面のドラフトを作成(案件一覧 → ヒアリング → 見積作成(松竹梅) → 契約 の流れ)
2. キャンバス上でレビュー・修正指示 → 確定した画面から実装に落とす
3. スマホ縦(現場)とタブレット横(商談・提示)の2サイズを基準にする
